# FailureLab

A C++20 portfolio project for investigating retries, deadlines and circuit breakers with a
**deterministic, single-threaded discrete-event simulation**. Run local experiments, compare
four strategies, and inspect reproducible JSON, CSV and text reports. No accounts or services
are needed at runtime.

FailureLab models one workload generator calling one downstream service. It makes no network
calls and never sleeps. It helps explain reliability-policy tradeoffs; it does not measure
real systems or prove production performance. There is no queueing, CPU contention, capacity,
connection pool or retry-induced overload model. More attempts measure traffic amplification;
they do not make the modeled service slower.

## Build and test

Targets: Linux (GCC/Clang) and macOS (Apple Clang), C++20, CMake 3.25+, Ninja, Python 3.9+.
Windows is outside this release. Debug/release builds and tests have passed on Linux
(GCC/Clang) and macOS, with ASan/UBSan also checked locally and on Linux CI. See the complete
[validation record](docs/validation.md).

Install build tools through your package manager, or in a local virtual environment:

```sh
python3 -m venv .tools
. .tools/bin/activate
python -m pip install cmake==3.31.6 ninja==1.11.1.3 clang-format==18.1.8 clang-tidy==18.1.8
cmake --preset debug
cmake --build --preset debug --parallel 4
ctest --preset debug
cmake --preset release
cmake --build --preset release --parallel 4
ctest --preset release
```

First configuration downloads SHA-256-verified nlohmann/json 3.11.3 and doctest 2.4.11 source
archives. Internet access is needed then; no global C++ dependencies are required. The first
`pip install` also needs internet. See [development](docs/development.md) for offline overrides,
sanitisers, formatting, analysis and installation. This repository has no public license for
its original source; see [third-party notices](THIRD_PARTY.md).

## Run a local binary archive

To prepare a shareable archive on your own machine after building release:

```sh
cmake --build --preset release --target package
python3 scripts/package_smoke.py build/release/packages/*.tar.gz
```

Extract the resulting archive under `build/release/packages/`, then run from its root:

```sh
bin/failurelab compare --config share/failurelab/scenarios/recovery.json --output results/comparison
```

Recipients need no CMake, compiler or Python to run that executable. The archive is specific to
its build OS/CPU and uses system libraries; compatibility with older systems is not promised.
macOS archives are unsigned and unnotarized. `README.txt` inside the archive gives exact commands.
No archive is published or uploaded by these commands or by CI.

## Five-minute demo

From the repository root after building release:

```sh
build/release/failurelab --help
build/release/failurelab --version
build/release/failurelab validate --config scenarios/recovery.json
build/release/failurelab run --config scenarios/recovery.json --strategy baseline --output results/baseline
build/release/failurelab compare --config scenarios/recovery.json --output results/comparison
cat results/comparison/summary.txt
python3 -m json.tool results/comparison/failurelab-report.json
```

The output directory also contains `results.csv`. Existing destinations fail with exit 4.
Add `--overwrite` to explicitly replace an existing FailureLab report directory. Directories
containing extra files are refused so personal notes cannot be silently deleted. Reproduce
an experiment using its saved configuration and seed:

```sh
build/release/failurelab compare --config scenarios/recovery.json --seed 42 --output results/reproduced
build/release/failurelab run --config scenarios/slow.json --strategy breaker --trace-limit 500 --output results/trace
```

`--trace-limit` caps detailed events **per strategy**, defaults to zero, and never affects
simulation results. JSON exposes `trace_truncated`. An effective normalized configuration is
saved in each JSON report under `configuration`; save that object as a scenario to replay a
report after editing the original file. Application version also matters for reproducibility.

## Actual recovery comparison

Generated by the release executable with `scenarios/recovery.json`, seed 42. The dependency
fails during `[300, 1000)` simulated milliseconds. See the complete generated
[report](examples/recovery/failurelab-report.json), [CSV](examples/recovery/results.csv) and
[terminal summary](examples/recovery/summary.txt).

| --- | ---: | ---: | ---: | ---: |
| baseline | 130 / 200 | 200 | 1.000 | 29 |

Retries recover some requests near the end of the outage, while nearly doubling attempts.
The breaker makes fewer downstream calls but rejects requests during its open/probe periods;
it succeeds less often here. A low latency percentile can reflect fast rejection, so read it
together with success rate. Fixed and exponential policies need not have equal latency or
attempt counts. Different retry timing can enter different behavior windows, even though
service random samples are coupled by request/attempt identity.

## Configuration

All durations are nonnegative integer milliseconds; deadlines, attempt timeouts and breaker
open duration must be positive. Unknown keys, duplicate keys, overlapping windows and invalid
ranges are errors. There are no silently supplied scenario defaults. Example complete file:

```json
{
  "schema_version": 1,
  "name": "Small transient experiment",
  "seed": 42,
  "request_count": 100,
  "arrival_interval_ms": 10,
  "deadline_ms": 400,
  "attempt_timeout_ms": 80,
  "service": {
    "latency": {"type": "uniform", "min_ms": 10, "max_ms": 30},
    "failure_probability": 0.25
  },
  "windows": [],
  "retry": {"max_attempts": 4, "base_delay_ms": 20, "max_backoff_ms": 160, "full_jitter": true},
  "circuit_breaker": {"failure_threshold": 5, "open_duration_ms": 150}
}
```

Bundled scenarios: `healthy`, `transient`, `recovery`, `slow`, and `isolation`. Each uses 200
requests. Fixed latency uses `{"type":"fixed","value_ms":20}`. Full details and resource
limits are in [configuration reference](docs/configuration.md).

## Metrics and interpretation

- Success rate = successful logical requests / offered logical requests. Final failures
  partition into service error, timeout, deadline or circuit-open rejection.
- Amplification = downstream attempts actually started / offered logical requests. Retry
  attempts exclude every request's first attempt; rejected admissions are not attempts.
- Latency = arrival to final logical outcome, including waits and fast rejections. Percentiles
  use nearest rank `ceil(p*N/100)` of sorted integer values; success-only percentiles exclude
  failed requests. Empty success subsets yield JSON `null` and blank CSV cells.
- Arrival duration = last arrival minus first arrival. Completion duration = last logical
  final outcome minus first arrival (at time zero). Throughput = successful logical requests
  / completion duration in seconds; a zero duration yields `null`, including zero-time runs.
- Downstream drain duration includes late downstream completions. Attempt errors/timeouts
  count the first settlement only; late responses cannot change outcomes or breaker state.
- Breaker transitions include timestamps; state durations cover `[0, completion_duration]`.
  Non-breaker strategies have no breaker durations. JSON holds the full transition list;
  CSV holds duration totals and transition count.

Exact deadlines and timeout ties, breaker generations, filesystem guarantees and reproducibility
boundaries are documented in [architecture](docs/architecture.md) and
[breaker semantics](docs/circuit-breaker.md).

## Repository

`include/failurelab/model.hpp` defines domain values and public interfaces. `src/config.cpp`
validates inputs; `policy.cpp` implements randomness, retries and the breaker; `simulation.cpp`
runs typed events; `report.cpp` serializes and stages reports; `main.cpp` handles CLI concerns.
`tests/`, `scenarios/`, `scripts/` and `.github/workflows/` provide verification and examples.

## Troubleshooting

Use `validate` first: errors name a JSON field or path. Exit codes are 0 success, 2 CLI usage,
3 configuration, 4 report I/O and 5 internal error. Normal output goes to stdout, errors to
stderr without stack traces. A failed supplied scenario never falls back to another scenario.

For download failures, check network access and proxy settings; dependency hashes are mandatory.
For stale output use a fresh directory or `--overwrite`. After a process crash, inspect the
sibling `.failurelab-lock` directory before manually removing it; it may hold a recoverable
previous report. Do not delete a lock while another FailureLab process is writing.
On modern Apple SDKs, clang-tidy must match the SDK compiler; the native analyzer script is
available when the pinned Linux clang-tidy cannot parse newer libc++ headers.
